전사 AI TFT · 마케팅팀 3개 과제 기반 · 2026.07

01현황과 목표

마케팅팀은 3개 업무 자동화 과제를 각각 독립 웹 앱으로 구축했다. 이제 목표는 이들을 재사용 가능한 Agent 단위로 재구성하고, 사용자가 하나의 창구에서 모든 업무를 처리할 수 있는 통합 Agent(오케스트레이터)로 묶는 것이다. 이 구조가 자리잡으면 이후 다른 팀의 자동화 과제도 같은 틀에 꽂아 넣기만 하면 된다.

TRAFFIC

웹사이트 트래픽 보고서 자동 생성

GA 13개 계정 수기 취합 → GA 연동 대시보드 + PDF 월간 보고서. 월 7.5h → 1h.

남은 과제 · 과거 2년치 보고서를 학습해 월별 인사이트 코멘트 자동 도출

NEWS

RSS 뉴스 자동 수집·분류 대시보드

수동 검색·분류 → RSS 자동 수집 + 경쟁사/산업/유형 자동 분류. 월 20h → 2h.

남은 과제 · Trend Report 초안 자동 작성, 주요 뉴스 요약 + 유관부서 메일링

WELMATE

웰메이트 트래킹 에이전트

온보딩 버디 배정·교육·서베이·활동비를 수기 관리 → 웰메이트 OS로 통합. 월 5~6h → 2h.

남은 과제 · 엔드서베이 결과 분석 자동화, 접근성 고도화

세 과제의 공통 패턴: ① 정기적 데이터 수집 → ② 정리·분류·계산 → ③ 사람이 읽을 산출물(보고서·메일·명단) 생성. 이 패턴을 표준 Agent 모듈로 정의하면, 개별 구현을 반복하지 않고 조립할 수 있다.

02설계 원칙

1. 도메인별 독립 Agent, 표준 인터페이스로 연결

하나의 거대 Agent에 모든 기능을 넣지 않는다. 업무 영역마다 Agent를 독립적으로 만들고(각 팀이 소유), 통합 Agent는 표준화된 도구 호출(MCP)로만 접근한다. 팀별 개발·배포·장애가 서로 격리된다.

2. 결정적 파이프라인과 LLM 추론의 분리

데이터 수집·집계·발송처럼 항상 같은 결과가 나와야 하는 작업은 스케줄 잡(코드)으로, 인사이트 도출·분류·초안 작성처럼 판단이 필요한 작업만 LLM에 맡긴다. 비용·오류·재현성 모두에서 유리하다.

3. 사람이 최종 승인하는 지점을 명시

외부로 나가는 것(메일 발송, 보고서 배포, 활동비 지급)은 반드시 초안 → 사람 승인 → 실행 단계를 거친다. Agent는 초안까지, 실행 버튼은 사람이 누른다.

4. 데이터는 공용 저장소에, 권한은 Agent 단위로

각 앱이 데이터를 따로 들고 있으면 통합 질문에 답할 수 없다. 공용 DB(Supabase)에 적재하되, 개인정보(웰메이트 인사 데이터)는 해당 Agent 내부에서만 접근하고 통합 Agent에는 요약만 전달한다.

04표준 Agent 모듈 — 모든 Agent가 따르는 공통 규격

각 도메인 Agent는 아래 4개 블록 + 매니페스트로 구성한다. 신규 Agent는 이 템플릿(Starter Kit)을 복제해서 시작한다.

① Tools — 도구 (동기 API)
  • 조회·계산·초안 생성 등 요청-응답형 기능
  • MCP 도구로 노출, 입출력 JSON 스키마 고정
  • 오케스트레이터가 호출하는 유일한 창구
② Jobs — 스케줄 파이프라인
  • 수집·집계·발송 등 반복 배치 (코드로 결정적 실행)
  • 공용 스케줄러에 등록, 실패 시 재시도·알림
③ Knowledge — 지식 저장소
  • 과거 보고서, 분류 기준, 메일 템플릿 등 RAG 소스
  • 공용 pgvector에 Agent별 네임스페이스로 적재
④ Skills — LLM 추론
  • 인사이트 도출, 분류, 요약, 초안 작성 등 판단이 필요한 단계만 LLM 호출
  • 프롬프트를 코드와 함께 버전 관리

Agent Manifest (agent.json)

Agent마다 선언 파일 하나를 두고 오케스트레이터가 이를 읽어 자동 등록한다 — 신규 Agent 연결이 "매니페스트 등록" 한 단계로 끝나는 이유.

  • name / description — 오케스트레이터의 라우팅 판단에 쓰이는 설명 (어떤 질문이 이 Agent 소관인지)
  • tools[] — 도구 목록과 입출력 스키마
  • permissions — 이 Agent를 호출할 수 있는 사용자/그룹, Agent가 접근하는 데이터 범위
  • events[] — 발행하는 이벤트 목록 (알림 라우터가 구독)
  • owner — 담당 팀/담당자 (장애·문의 라우팅)

06연동 방식 — 통합 Agent가 도메인 Agent를 부리는 법

연동 경로는 두 가지뿐이다. 사용자가 물어볼 때(Pull)는 오케스트레이터의 도구 호출, 시스템이 먼저 알릴 때(Push)는 이벤트 버스. 이 둘을 섞지 않는 것이 운영 단순성의 핵심이다.

Pull — 대화형 질의 처리

1. 사용자 질의"6월에 Broadband 사이트 트래픽 왜 떨어졌어?"
→
2. 라우팅·계획오케스트레이터가 Traffic + News 두 Agent 소관으로 판단, 호출 순서 결정
→
3. 도구 호출get_traffic_summary로 수치 확보 → search_news로 같은 기간 업계 동향 확보
→
4. 종합 응답수치 + 업계 컨텍스트를 근거로 원인 가설과 출처를 함께 제시

단일 Agent 질의("이번 달 온보딩 현황은?")는 2단계에서 해당 Agent 도구 하나만 호출하고 끝. 복합 질의만 플래너가 개입한다.

Push — 프로액티브 알림

1. Agent가 이벤트 발행traffic.anomaly, news.important, welmate.survey_due …
→
2. 알림 라우터이벤트별 구독 규칙(누구에게·어느 채널로)에 따라 배달 결정
→
3. 채널 배달Teams 메시지 / 메일. 메시지에 통합 챗으로 이어지는 후속 질문 링크 포함

  • 오케스트레이터가 사용자 신원을 모든 도구 호출에 전달 → Agent가 자체 권한 규칙으로 최종 판단 (예: 활동비 명단은 담당자만)
  • 외부 시스템 자격증명(GA 서비스 계정 키, Graph 토큰)은 Agent별 시크릿 저장소에 격리
감사·품질·비용
  • 모든 도구 호출을 감사 로그에 기록 (누가·언제·무엇을·어떤 결과)
  • Agent별 LLM 토큰 비용 집계 → 월간 리포트
  • 회귀 평가셋: 대표 질의 목록을 정기 실행해 라우팅·답변 품질 저하 감지
  • 외부 발신(메일·보고서 배포)은 예외 없이 사람 승인 게이트

08단계별 로드맵

P0
기반 표준화~1개월 · 기존 앱 3개 정비
  • 공용 Supabase 프로젝트로 데이터 통합 (Agent별 스키마 분리, 인사 데이터는 RLS로 격리)
  • GA4 서비스 계정 전환 → 트래픽 수집 완전 무인화
  • 흩어진 스케줄 작업을 공용 스케줄러로 일원화
  • Agent Manifest 규격 확정, 3개 앱에 각각 작성
P1
Agent화 + 통합 챗 MVP1~2개월
  • 각 앱의 핵심 기능을 MCP 도구 서버로 노출 (앱당 도구 3~5개면 충분)
  • 오케스트레이터 구축: Claude API 기반, 라우팅 + 단일 Agent 질의부터
  • 사내 웹 챗 배포 → 마케팅팀 내부 파일럿
P2
지능화 + 프로액티브2~3개월
  • 이벤트 버스 + 알림 라우터 (Teams/메일) — 이상 감지·마감 리마인드
  • Knowledge 계층 구축: 과거 보고서 RAG → 트래픽 인사이트·Trend Report 초안 자동화 (각 과제의 "후속 Action" 해소)
  • 복합 질의 플래너 (교차 시나리오 지원), 엔드서베이 분석 자동화
P3
전사 확장이후 지속
  • Agent Starter Kit 배포: 매니페스트 + 도구 서버 템플릿 + 배포 파이프라인 → 타 팀이 자기 과제를 같은 규격으로 Agent화
  • Agent Registry: 매니페스트 등록만으로 통합 챗에 자동 연결
  • 거버넌스 정착: 권한 심사, 비용 상한, 품질 평가 프로세스

09기술 스택 권장안
